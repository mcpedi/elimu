
# Report-card implementation notes

The project already has school-scoped academic years, terms, classes, subjects, assessments, marks, the `school.academics.config` query, and the `assertTeacherAssignment` helper. Teacher/class-teacher academic actions are guarded by `academicRoles` plus class/subject assignment checks, while administrative academic roles bypass assignment checks. Existing finance documents use a branded HTML document, popup print flow, and a separate audited export mutation; the report-card PDF flow should follow the same browser Print/Save PDF pattern and only audit after a popup opens.

The report-card design adds one durable `reportCards` row per learner and term, with a JSON result snapshot, summary marks, overall grade, teacher comment, school/class/year/term foreign keys, and created/updated actors. The learner portal currently renders student-only content through `LinkedLearnerPanel` and `PortalAcademicPanel`; parents should not receive report-card rows unless explicitly added later. The teacher creation form belongs in `AcademicsPanel` beside assessment and mark entry and should reuse the existing workflow card selectors.

## Preview and batch contract planning

The existing `reportCards.create` implementation already contains the canonical snapshot algorithm and school/term/class validation. The new preview should reuse that algorithm conceptually but return an unsaved per-learner snapshot and never write `reportCards`, `reportExports`, or audit events. The batch operation should accept one class, academic year, term, optional title, and optional teacher comment; enforce the same teacher/class authorization and term scope; process active learners in the selected class; upsert one card per learner; and return per-learner statuses so missing marks do not hide which learners were skipped. A batch audit should summarize created, updated, and skipped counts without logging learner credentials or document contents. The existing router already imports all required tables and grading helpers; the implementation can add a shared snapshot builder beside `getOperatingSchool` and expose `preview` plus `batchGenerate` under the existing `school.reportCards` router. No schema migration is required because preview is ephemeral and batch writes existing `reportCards` rows.

The publication-state desktop and mobile shell screenshots remain stable after the new controls; the Academics workflow remains reachable through the authenticated module navigation. Publication-state review found `reportCards.publishedAt` is currently non-null with a default timestamp, so generated cards cannot remain drafts. The state contract will make `publishedAt` nullable, add a migration that preserves existing published timestamps, and have learner retrieval filter `isNotNull(reportCards.publishedAt)`. Batch generation will explicitly create/update drafts with `publishedAt: null`; publish/unpublish will set or clear the timestamp and audit one batch summary. Migration `0007_keen_morg.sql` safely changes only `reportCards.publishedAt` to nullable, preserving existing timestamps. The router now filters learner retrieval to published cards, returns scoped batchStatus counts, and exposes idempotent publishBatch/unpublishBatch mutations with audit summaries.
